# ML- и LLM-задачи в системе

---

## 1. Что чем решается и почему

Главный принцип: **самый простой инструмент, который решает задачу с нужным
качеством.** Модель добавляется там, где правило не справляется, LLM — там,
где нужен свободный текст.

| Задача | Подход | Почему именно так | Где не подошло бы другое |
|---|---|---|---|
| Маскирование PII (персональных данных) | **Правила** (регулярные выражения) | Форматы телефона, почты, карты фиксированы. Нужна воспроизводимость и 100% предсказуемость | Модель может пропустить номер карты «иногда» — недопустимо для требования не отправлять PII вовне |
| Детекция prompt injection | **Правила** + список паттернов | Защита не должна зависеть от компонента, который атакуют | LLM-детектор сам уязвим к инъекции |
| Списки запрещённых к автозакрытию категорий | **Правила** | Это бизнес-политика, а не статистика. Меняется решением руководителя, а не переобучением | Модель здесь просто не нужна |
| Классификация темы (8 категорий) | **Классическая ML-модель**: логистическая регрессия поверх эмбеддингов | Фиксированный набор классов, десятки тысяч размеченных примеров, требование ~5 мс и объяснимой уверенности | LLM: 4,2 с и высокая стоимость на объёме 360 тыс./мес при сопоставимом качестве |
| Оценка приоритета и тональности | **Классическая ML-модель** | То же самое, что классификация | |
| Поиск статьи базы знаний, поиск дублей и похожих тикетов | **Embeddings + retrieval** (векторный поиск) | Нужна семантическая близость: «где посылка» и «заказ не приехал» — один смысл, ноль общих слов | Полнотекстовый поиск не находит перефразировки; LLM здесь избыточен |
| Генерация черновика ответа | **LLM** | Свободный текст, естественная формулировка под контекст клиента | Шаблоны дают жёсткий канцелярит и не покрывают вариативность |
| Суммаризация длинной переписки для оператора | **LLM** | Сжатие произвольного текста | |
| **Где LLM использовать НЕ стоит** | | | |
| Решение об автозакрытии тикета | Только policy engine на правилах и порогах | Решение должно быть детерминированным, объяснимым и воспроизводимым через год при разборе жалобы | LLM не даёт калиброванной вероятности и не воспроизводится побитово |
| Извлечение номера заказа | Регулярное выражение | Формат известен, точность 100%, стоимость 0 | Платить за LLM-вызов ради `\d{4,8}` — расточительство |
| Расчёт SLA, приоритетов, сумм возврата | Код | Арифметика | LLM ошибается в арифметике и это невозможно гарантированно исправить промптом |

## 2. Откуда берутся модели

| Модель | Происхождение | Лицензия | Какие данные нужны |
|---|---|---|---|
| `multilingual-e5-small` (эмбеддинги, 384 измерения) | **Открытая, берём как есть** | MIT | Не требует дообучения на старте |
| Классификатор темы | **Обучаем внутри** — логистическая регрессия поверх эмбеддингов | — | ~20 000 размеченных исторических тикетов |
| `rubert-tiny2` (запасной вариант классификатора) | **Открытая, дообучаем внутри** | MIT | Те же 20 000 тикетов; берём, если линейная модель не даст целевого качества |
| Детекторы риска | **Правила, пишем сами** | — | Список паттернов + разметка 2 000 тикетов для проверки полноты |
| Генерация ответа | **Внешний API** (Claude) | Коммерческий | Не обучаем; данные не уходят на обучение вендора по условиям API |

Обучение большой модели внутри **не планируется**: объём данных (десятки тысяч
тикетов) и задача (8 классов) не оправдывают затрат, а качество открытых
эмбеддингов на русском языке достаточно.

## 3. Технические метрики выбора моделей

### Классификация темы

**macro-F1** — среднее значение F1 по всем категориям, каждая категория весит
одинаково независимо от того, сколько в ней тикетов.

```
F1_k = 2 · P_k · R_k / (P_k + R_k)
P_k  = TP_k / (TP_k + FP_k)          — precision (точность) по категории k
R_k  = TP_k / (TP_k + FN_k)          — recall (полнота) по категории k
macro-F1 = (1/K) · Σ F1_k
```
где `TP_k` (True Positive) — тикеты категории k, распознанные верно;
`FP_k` (False Positive) — тикеты других категорий, ошибочно отнесённые к k;
`FN_k` (False Negative) — тикеты категории k, отнесённые к другой категории;
`K` = 8 — число категорий.

Macro, а не micro (взвешенное по объёму): редкая категория `account_access`
несёт максимальный риск, и её нельзя «усреднить» большим `delivery_status`.

**Precision при высокой уверенности** — ключевая метрика для автоответа:

```
P@τ = (число верных решений среди тикетов с уверенностью ≥ τ) / (число тикетов с уверенностью ≥ τ)
```
где `τ` (тау) — порог уверенности. Именно эту метрику мы максимизируем при
подборе `τ`: для автозакрытия допустима низкая полнота, но не низкая точность.

| Метрика | Целевое значение для приёмки |
|---|---|
| macro-F1 на отложенной выборке | ≥ 0,80 |
| P@τ для категорий автозакрытия | ≥ 0,97 |
| Латентность инференса p95 | ≤ 50 мс |
| Размер модели | ≤ 500 МБ (помещается в память сервиса) |

### Поиск (retrieval)

**Recall@k** — доля запросов, где нужная статья попала в топ-k выдачи:
```
Recall@k = (число запросов, где верная статья в топ-k) / (общее число запросов)
```

**MRR** (Mean Reciprocal Rank — средний обратный ранг):
```
MRR = (1/N) · Σ (1 / rank_i)
```
где `rank_i` — позиция верной статьи в выдаче для i-го запроса, `N` — число
запросов. Если верная статья на 1-м месте — вклад 1,0; на 3-м — 0,33.

| Метрика | Целевое значение |
|---|---|
| Recall@3 | ≥ 0,90 |
| MRR | ≥ 0,75 |

### Генерация

**Groundedness** (обоснованность) — доля утверждений в ответе, подтверждаемых
текстом найденной статьи:
```
Groundedness = (число утверждений с опорой на статью) / (общее число утверждений в ответе)
```
Измеряется на выборке 200 ответов: сначала разметкой людьми при приёмке, далее
LLM-as-judge (LLM в роли оценщика) с калибровкой по человеческой разметке
раз в месяц.

| Метрика | Целевое значение |
|---|---|
| Groundedness | ≥ 0,95 |
| Доля ответов с явной ссылкой на статью базы знаний | 100% |
| Доля ответов, содержащих обещание денег/скидки (запрещено) | 0 |

## 4. Baseline-лестница: с чего начинаем

Порядок продуман так, чтобы каждая ступень давала работающую систему, а не
задел на будущее.

| Ступень | Что | Зачем |
|---|---|---|
| **0. Правила + TF-IDF** | Ровно то, что в PoC этого репозитория | Даёт нижнюю границу качества за день работы и вскрывает проблемы данных до обучения моделей |
| **1. Эмбеддинги + логистическая регрессия** | multilingual-e5-small + линейный классификатор | Основной кандидат. Быстро, дёшево, калибруемо |
| **2. Дообученный rubert-tiny2** | Fine-tuning на 20 тыс. тикетов | Берём, только если ступень 1 не дотянула до macro-F1 0,80 |
| **3. Каскад** | Ступень 1 на 90% трафика, LLM-классификация на остатке с низкой уверенностью | Берём, только если анализ ошибок покажет, что остаток однороден и дорог |

Ступень 3 намеренно последняя: она добавляет зависимость от внешнего API
в горячий путь, чего архитектура старается избежать.

## 5. Как валидируем качество

**Разбиение по времени, а не случайное.** Обучение — тикеты за месяцы 1–4,
валидация — месяц 5, тест — месяц 6. Случайное разбиение завышает метрики:
всплеск обращений об одном инциденте попадёт и в обучение, и в тест, и модель
покажет качество, которого на новых данных не будет. Разбиение по времени
воспроизводит реальную ситуацию — модель всегда работает на данных из будущего
относительно обучения.

**Три уровня проверки, в этом порядке:**

| Уровень | Что проверяем | Длительность | Критерий перехода дальше |
|---|---|---|---|
| Offline | macro-F1, Recall@3, P@τ на отложенном тесте | 2 дня | macro-F1 ≥ 0,80 |
| Shadow | Модель считает решения на 100% живого трафика, но ничего не делает. Сравниваем с фактическими действиями операторов | 2 недели | Расхождение с операторами объяснимо, нет систематического сдвига по категориям |
| Online | Suggest, затем автозакрытие на растущей доле трафика | 3–4 недели на этап | Guardrail-метрики в норме (docs/monitoring.md) |

Shadow-режим — самый недооценённый этап: он ловит расхождение распределений
между историческими данными и живым трафиком **без единого риска для клиента**.

## 6. Обработка низкой уверенности

Модель обязана уметь **отказываться отвечать**. Это отдельно проектируемое
поведение, а не побочный эффект.

**Калибровка.** Сырой выход классификатора — не вероятность. Применяется
Platt scaling (логистическая калибровка): поверх выхода модели обучается
одномерная логистическая регрессия на валидационной выборке, после чего
«уверенность 0,9» действительно означает «в 90% таких случаев модель права».
Без калибровки пороги подобрать невозможно — они будут означать разное для
разных категорий.

**Пороги и что происходит ниже них** (реализовано в `poc/policy.py`):

| Условие | Действие | Правило в PoC |
|---|---|---|
| Уверенность < 0,30 | Общая очередь разбора, тема не проставляется | П-3 |
| 0,30 ≤ уверенность < 0,55 | Маршрутизация в профильную очередь + черновик оператору | П-7 |
| Уверенность ≥ 0,55 **и** отрыв от 2-й категории ≥ 0,15 **и** категория безопасна **и** риск низкий **и** найдена статья | Автоответ | П-6 |

**Почему отдельно проверяется отрыв (margin) от второй категории.** Ситуация
«delivery_status 0,56 против cancel_order 0,55» формально проходит порог
уверенности, но фактически модель бросила монетку. Отрыв ловит именно этот
случай — самый опасный для автоответа.

**Отказ модели — это успех, а не ошибка.** Доля отказов отдельно
отслеживается: её резкий рост означает сдвиг данных (см. docs/monitoring.md),
а не поломку.

## 7. Разметка исторических данных

| Параметр | Значение | Обоснование |
|---|---|---|
| Объём | 20 000 тикетов | ~2 500 на категорию: достаточно для линейной модели поверх готовых эмбеддингов |
| Отбор | Стратифицированная выборка по категориям и месяцам + все тикеты с reopen | Редкие категории иначе не наберут объём; reopen — самые информативные случаи |
| Кто размечает | Подрядчик (2 человека) + саппорт-лид как арбитр | Операторы знают домен, но их время дороже |
| Что размечаем | Категория, флаги риска, «можно ли было ответить автоматически» | Третья метка — прямой таргет для оценки потенциала автоматизации |
| Гайдлайн | 1 страница: определение каждой категории + 3 примера + 2 пограничных случая | Длинные гайдлайны не читают |
| Двойная разметка | Первые 2 000 тикетов размечают оба разметчика независимо | Проверка согласованности до основного объёма |
| Контроль качества | Cohen's kappa ≥ 0,7 | См. формулу ниже |
| Срок | 3 недели | 20 000 / (2 чел. × 250 тикетов/день) ≈ 40 рабочих дней ≈ 3 недели на двоих |
| Стоимость | ≈ 240 000 руб | Допущение: 12 руб за размеченный тикет |

**Cohen's kappa (каппа Коэна)** — мера согласованности двух разметчиков
с поправкой на случайные совпадения:
```
κ = (p_o − p_e) / (1 − p_e)
```
где `p_o` (observed agreement) — доля тикетов, где разметчики совпали;
`p_e` (expected agreement) — доля совпадений, ожидаемая при случайной разметке
с теми же частотами категорий.

Поправка нужна, потому что при 8 категориях с перекосом в сторону
`delivery_status` двое случайных разметчиков совпадут примерно в 30% случаев,
и «согласованность 70%» без поправки ничего не значит. κ = 0,7 — общепринятая
граница приемлемого согласия.

**Если κ < 0,7** — проблема не в разметчиках, а в определениях категорий:
таксономия пересматривается, спорные категории объединяются или разделяются,
разметка перезапускается. Это дешевле, чем обучать модель на противоречивых
метках.

**Разметка продолжается после запуска.** Правки операторов в suggest-режиме —
это бесплатный поток свежей разметки, покрывающий именно те случаи, где
система ошибается.
